# Replace CONTEXT.md Bootstrapping with an Architecture Map

## Problem Statement

The tool currently ships a `BootstrapContextCommand` (`app:bootstrap-context`) that writes a `CONTEXT.md` glossary template into an analyzed project. This conflates two unrelated jobs: authoring a project's ubiquitous-language glossary (a human/domain judgment call) and running static architecture analysis (a deterministic, tool-driven job). The glossary-seeding behavior was a deliberate early decision — recorded in this repo's own `CONTEXT.md` "Next Steps" — but it doesn't belong in this tool.

Separately, `analyse` currently defaults to writing its output (`architecture.json`, `graph.svg`, `report.html`) either directly into the analyzed project's root or into a `build/` directory inside the analyzed project (per the Makefile's `OUTPUT ?= $(PROJECT)/build/architecture` default). This means the tool leaves a footprint inside repos it only has read access to analyze, which contradicts the project's own principle that the tool must not make or assume architecture decisions inside someone else's repo.

Agents and humans working on unfamiliar legacy PHP/CakePHP codebases also currently have to consume the fine-grained, per-class `architecture.json` IR to get any sense of the codebase's shape, which costs significant tokens/time before an agent can even start reasoning about where to look.

## Solution

Remove `BootstrapContextCommand` entirely, along with its bin wiring, template resource, README section, and the CONTEXT.md seeding policy sentence it implemented. `CONTEXT.md` authoring for analyzed projects becomes a manual or Agent-Skill-driven task, fully outside this tool's responsibility.

Rename the CLI entrypoint from `bin/bootstrap-context` to `bin/architecture-discovery`, since only the `analyse` command remains behind it.

Add a new artifact, the **Architecture Map** (`architecture-map.md`), generated by `analyse` as a Markdown summary of the architecture model at module/cluster granularity — cluster identifiers, member class counts, external coupling, inter-cluster dependency direction, and detected framework relations. It deliberately excludes per-class detail (already available in `architecture.json`) and excludes ubiquitous-language/domain-terminology content (which stays the responsibility of `CONTEXT.md`). It is generated by default alongside the other `analyse` outputs and can be excluded via `--format`.

Change `analyse`'s default output location so that omitting `--output` writes to `out/<project-name>/` inside this tool's own repo, rather than into the analyzed project. The `--output` option remains available to override this for anyone who deliberately wants artifacts elsewhere. The Makefile and Docker-based workflow defaults are updated to match, so the default `make analyse PROJECT=...` invocation no longer writes into the target project's directory tree.

## User Stories

1. As a maintainer of this tool, I want `BootstrapContextCommand` removed entirely, so that this tool no longer authors glossary content inside repos it analyzes.
2. As a user of this tool, I want `CONTEXT.md` generation in analyzed projects to be a manual or Agent-Skill task, so that domain-language authoring stays a human/agent judgment call rather than a templated CLI side effect.
3. As a contributor, I want the bin entrypoint renamed to `bin/architecture-discovery`, so that the executable name matches the tool's actual purpose now that `bootstrap-context` no longer exists.
4. As an agent exploring an unfamiliar legacy PHP/CakePHP codebase, I want a compact Architecture Map summarizing module/cluster boundaries, so that I can orient myself without reading the full `architecture.json` or the codebase itself.
5. As an agent consuming the Architecture Map, I want cluster-level external coupling and inter-cluster dependency direction, so that I can identify which parts of the codebase are structurally central versus peripheral before making changes.
6. As an agent consuming the Architecture Map, I want detected framework relations (e.g. CakePHP ORM associations, dynamic resolvers) surfaced at the cluster level, so that I understand which coupling is framework noise versus domain-relevant.
7. As a user running `analyse`, I want the Architecture Map generated by default alongside the other output formats, so that I get the token-efficient summary without needing to opt in explicitly.
8. As a user who doesn't want the Architecture Map, I want to exclude it via `--format`, so that I retain control over which artifacts are produced, consistent with the other output formats.
9. As a user of this tool, I want `analyse`'s default output directory to live inside this tool's own repo (`out/<project-name>/`) when `--output` is omitted, so that running an analysis never writes anything into the project being analyzed.
10. As a user who wants output somewhere specific, I want `--output` to still override the default location, so that I retain full control when the default doesn't fit my workflow.
11. As a user of the Dockerized `make analyse` workflow, I want the default `OUTPUT` to point inside this repo rather than inside the target project, so that the Make-based workflow is consistent with the CLI's own default behavior.
12. As a maintainer, I want the documentation (`README.md`, `docker/README.md`, `Makefile` help text) updated to reflect the new bin name, the removed bootstrap command, and the new default output location, so that instructions don't reference removed or incorrect behavior.
13. As a maintainer, I want this repo's own `CONTEXT.md` updated to drop the CONTEXT.md-seeding "Next Steps" sentence and record the new Architecture Map / no-footprint-in-analyzed-repo decisions, so that the glossary stays accurate to current tool behavior.
14. As a maintainer, I want an ADR recording why CONTEXT.md-seeding was removed and why the tool never writes into analyzed repos, so that a future reader understands this wasn't an oversight but a deliberate reversal of an earlier decision.

## Implementation Decisions

- Delete `src/Application/Command/BootstrapContextCommand.php`, `resources/templates/CONTEXT.md`, and all references to `app:bootstrap-context` / `BootstrapContextCommand` (bin script's command registration, README section describing it).
- Rename `bin/bootstrap-context` to `bin/architecture-discovery`. Update the `bin` entry in `composer.json`, and all invocations in `Makefile`, `README.md`, and `docker/README.md`.
- Add a new `Reporting`-namespace renderer (parallel to the existing `GraphvizRenderer` and `HtmlReportGenerator`) responsible for producing the Architecture Map Markdown from an `Architecture` instance. It reads cluster data already present on `Architecture` (`getClusters()`, populated by `ConnectedComponentsClusterer`) plus dependency metadata (framework tags carried in `Dependency::getMetadata()`), and does not perform its own analysis — it is a pure presentation layer over the existing model, consistent with the "one canonical IR, multiple derived outputs" principle already used for `graph.svg`/`report.html`.
- Add `architecture-map` (or equivalent) as a recognized value for `AnalyseCommand`'s `--format` option, alongside the existing `json`, `dot`, `svg`, `html` values, and include it in the default format set so it's generated unless explicitly excluded.
- The Architecture Map content is restricted to: cluster id, member class count, internal/external dependency counts (already computed per-cluster by `ConnectedComponentsClusterer::calculateMetrics`), inter-cluster dependency direction, and framework-tagged relation counts. No per-class listings and no glossary/terminology content belong in this artifact.
- Change `AnalyseCommand`'s output-directory resolution: replace the current `$input->getOption('output') ?? $projectPath` fallback with a default of `out/<project-name>/` resolved relative to this tool's own repo root (not the analyzed project path). `--output` continues to take precedence when provided.
- Update `Makefile`'s `analyse` target default (`OUTPUT ?= $(PROJECT)/build/architecture`) to default inside this repo instead (e.g. `OUTPUT ?= out/$(notdir $(PROJECT))`), keeping the existing `OUTPUT=` override mechanism unchanged.
- Update `CONTEXT.md`: remove the "Next Steps" sentence about seeding `CONTEXT.md` in analyzed projects, and add an entry documenting the Architecture Map artifact and the "never write into the analyzed repo" output policy.
- Write an ADR (`docs/adr/`) covering both the removal of CONTEXT.md-seeding and the output-location policy change, since both stem from the same underlying principle and were made together as one decision.
- Update `README.md` and `docker/README.md` to remove the `bootstrap-context` usage example, reflect the renamed bin script, and correct the documented default output location.

## Testing Decisions

- Good tests here assert on external behavior — the generated Markdown content, the resolved output directory, and CLI exit codes/output — not on internal rendering implementation details.
- The new Architecture Map renderer is tested the same way `GraphvizRenderer`/`HtmlReportGenerator` are tested today (see `tests/Unit/Reporting/`): construct an `Architecture` fixture with known classes/dependencies/clusters, call `render()`, and assert on the resulting Markdown structure and content (cluster ids, counts, framework tags present).
- `AnalyseCommand`'s new default output-directory behavior is tested via `tests/Unit/Application/Command/AnalyseCommandTest.php` (existing seam): assert that running `analyse` without `--output` writes into `out/<project-name>/` relative to the tool repo and does not write anything into the analyzed fixture project's directory.
- `AnalyseCommand`'s `--format` handling is extended with a case verifying the Architecture Map is included by default and excluded when `--format` is given without it.
- No test seam is needed for the `BootstrapContextCommand` removal or the bin rename beyond the existing suite passing without any reference to the deleted class; there is no existing `BootstrapContextCommandTest` to remove.

## Out of Scope

- Any new automatic architecture decision-making (bounded-context naming, module ownership) inside the Architecture Map — it remains a presentation of detected facts, not a hypothesis-generation step (that remains the job of the existing/future LLM suggestion pipeline).
- Changes to the `architecture.json` schema or the LLM context-building pipeline (`ArchitectureContextBuilder`).
- A CLI or Agent Skill for authoring `CONTEXT.md` in analyzed projects — this spec only removes the old behavior; building a replacement authoring workflow is a separate effort.
- Backward-compatibility shims for the old `bin/bootstrap-context` name or the `app:bootstrap-context` command.

## Further Notes

This work reverses a decision recorded in this repo's own `CONTEXT.md` ("Next Steps" seeding sentence), so the CONTEXT.md update and ADR are integral parts of this spec, not optional cleanup — the codebase's own glossary must not describe removed behavior as intended.

The Architecture Map and the output-location change are shipped together because they share one principle: this tool only produces read-only insight about an analyzed project and never writes into it. The CONTEXT.md-seeding removal is part of the same principle applied to the glossary-authoring behavior specifically.
